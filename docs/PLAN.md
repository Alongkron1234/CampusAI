# CampusAI: แผนโครงงาน

ระบบถาม-ตอบเกี่ยวกับระเบียบและข้อบังคับของมหาวิทยาลัยภาษาไทย ใช้สถาปัตยกรรม RAG (Retrieval-Augmented Generation)
เวอร์ชันนี้เขียนใหม่ทั้งหมดตั้งแต่ศูนย์ เพื่อแก้ปัญหาของเวอร์ชันเก่าที่อ่าน PDF ได้ไม่ครบเพราะติด rate limit ของ Gemini API

---

## 1. ภาพรวม

### 1.1 เป้าหมาย
- อ่านเอกสารระเบียบ (PDF) ได้**ครบทุกหน้า** ทั้งไฟล์ที่มีข้อความในตัวและไฟล์ที่เป็นภาพสแกน
- ค้นได้ทั้งแบบระบุเลขข้อ/มาตรา ("ข้อ 15 ว่าอย่างไร") และแบบถามภาษาธรรมชาติ ("ทุจริตสอบโดนอะไร")
- ตอบจากเอกสารเท่านั้น อ้างอิงแหล่งที่มาทุกครั้ง และปฏิเสธเมื่อเอกสารไม่มีข้อมูล
- มีตัวเลขวัดผลที่พิสูจน์ได้ว่าระบบทำงานดีแค่ไหน

### 1.2 สิ่งที่ต่างจากเวอร์ชันเก่า

| ปัญหาเดิม | วิธีแก้ในเวอร์ชันนี้ |
|---|---|
| OCR ผ่าน Gemini ติด rate limit อ่านไม่ครบ | OCR บนเครื่องด้วย **Typhoon OCR** ผ่าน Ollama ไม่มี limit |
| ติด limit แล้วต้องเริ่มใหม่หมด | OCR ทีละหน้า และ **cache ผลทุกหน้าลงดิสก์** รันใหม่ก็ทำต่อจากที่ค้าง |
| ส่งไป OCR มากเกินจำเป็น | ตรวจรายหน้าก่อน OCR **เฉพาะหน้าที่ข้อความเสียหรือเป็นภาพสแกน** |
| Embedding ผ่าน Gemini ใช้โควตาร่วมกับ OCR | Embedding บนเครื่องด้วย **bge-m3** |
| บังคับใช้ Qdrant Cloud อย่างเดียว | รองรับ **ทั้ง Qdrant local mode และ Cloud** สลับได้ด้วย `.env` ตัวเดียว ไม่ต้องแก้โค้ด |
| Fallback chunk ตัดตาม "คำ" (ใช้กับภาษาไทยไม่ได้) | ตัดตามจำนวน**ตัวอักษร** |
| ไม่มี evaluation และไม่มี test | มี golden set + ตัววัด retrieval/คำตอบ + unit test + CI |


### 1.7 วิธีทำงาน
- **1 Issue = 1 branch = 1 PR** แตก branch จาก `main` ล่าสุด แล้ว merge กลับเมื่อผ่านเงื่อนไข "เสร็จเมื่อ"
- ชื่อ branch: `feat/…` ฟีเจอร์, `chore/…` งานโครงสร้าง/เครื่องมือ, `docs/…` เอกสาร
- ทุก PR ต้องผ่าน `ruff` และ `pytest` บน CI
- โค้ดที่มี logic ต้องมี unit test ส่วนที่เรียกโมเดลหรือ API ให้ mock ใน test
- **สร้างชุดวัดผลก่อนปรับจูน** ทุกการปรับปรุงต้องมีตัวเลขเทียบก่อนและหลัง
- ห้าม commit `.env`, `data/` และไฟล์ PDF

### Phase 1: Ingestion

เป้าหมาย: แปลง PDF ทุกไฟล์เป็น chunk ที่ข้อความถูกต้อง ครบทุกหน้า และมี metadata พอสำหรับอ้างอิง ขั้นนี้ทำบนเครื่องทั้งหมด ไม่เรียก API

#### #2 `feat/page-extraction`

**ทำอะไร**
- [ ] `pdf_text.py`: ดึงข้อความทีละหน้าด้วย pdfplumber
- [ ] ตัวตรวจ `needs_ocr(text)` คืนค่า (ต้อง OCR ไหม, เหตุผล) ถ้าเจออย่างใดอย่างหนึ่ง:
  - ข้อความสั้นหรือว่าง → น่าจะเป็นภาพสแกน
  - มี `(cid:` → ฟอนต์ไม่มีตาราง unicode
  - มีอักขระ Private Use Area (`U+F700–U+F8FF`) → ฟอนต์ไทยรุ่นเก่า
  - สระบน/ล่างหรือวรรณยุกต์ที่ไม่มีพยัญชนะนำ เกินสัดส่วนที่กำหนด → ข้อความเพี้ยน
- [ ] คำสั่ง `campusai check`: ตารางสรุปรายไฟล์ (จำนวนหน้า / หน้าที่ต้อง OCR / เหตุผล) มี `--verbose` ไว้ดูรายหน้า
- [ ] `ocr.py`: เรียก Typhoon OCR ผ่าน Ollama (OpenAI-compatible endpoint) ทีละหน้า
  - cache ที่ `data/cache/ocr/<sha256 ของไฟล์>/<ชื่อโมเดล>/<เลขหน้า>.md`
  - ถ้ามี cache แล้วให้ข้าม ไม่เรียกโมเดลซ้ำ
  - retry แบบเว้นระยะนานขึ้นเรื่อย ๆ เมื่อ Ollama ไม่ตอบ
  - แสดงความคืบหน้า (หน้าที่เท่าไร / ทั้งหมด, เวลาโดยประมาณ)
- [ ] Test: `needs_ocr` กับข้อความตัวอย่างทุกกรณี, logic ของ cache (mock ตัวเรียกโมเดล)

**เสร็จเมื่อ**
- รัน `check` กับ PDF จริงได้ และสุ่มดูด้วยตา 10 หน้าแล้วผลตรงกับที่ระบบตัดสิน
- OCR ได้ครบทุกหน้าที่ต้องทำ
- **กด Ctrl+C กลางทางแล้วรันใหม่ งานต้องทำต่อจากหน้าที่ค้าง** และรันซ้ำเมื่อครบแล้วต้องเสร็จทันที

**หมายเหตุ**: บน M5 คาดว่า OCR ได้หน้าละหลายวินาทีถึงหลายสิบวินาที ให้จดเวลาจริงไว้ใช้ในรายงาน

#### #3 `feat/ingest-pipeline`

**ทำอะไร**
- [ ] `clean.py`: ทำความสะอาดข้อความไทย
  - แก้ `ํา` → `ำ` และแก้วรรณยุกต์ที่สลับที่กับสระบน (`ท่ี` → `ที่`)
  - ลบอักขระ zero-width และช่องว่างซ้ำ
  - ลบเลขหน้า (`- 3 -`, `หน้า 3`, `3/10`) และเส้นคั่น
  - ลบแท็กที่ OCR สร้างขึ้น (คำบรรยายรูป/ตราสัญลักษณ์, เลขหน้า)
  - แปลงเลขไทยเป็นอารบิก ให้ "ข้อ ๑๕" กับ "ข้อ 15" ค้นเจอเหมือนกัน
- [ ] `chunker.py`: แบ่ง chunk ตามโครงสร้างเอกสาร
  - ตัดที่หัว `ข้อ N` / `มาตรา N` (รองรับ `N/M` และหัวที่มี markdown เช่น `**ข้อ 1**`)
  - จำว่าอยู่ใน `หมวด` / `ส่วนที่` ไหน
  - กันการตัดผิดจากบรรทัดที่ขึ้นต้นด้วย "ข้อ N" แต่เป็นการอ้างถึง: รับเป็นหัวข้อใหม่เฉพาะเมื่อเลขเพิ่มขึ้น (หรือเริ่ม 1 ใหม่เมื่อเป็นระเบียบฉบับใหม่)
  - ข้อที่ยาวเกินกำหนด (~1,200 ตัวอักษร) ให้ซอยตามบรรทัด และมีส่วนซ้อนทับ (overlap)
  - เอกสารที่ไม่มีโครงสร้างข้อ/มาตรา: ตัดตามจำนวนตัวอักษร (~1,000 ตัว, overlap ~200)
  - metadata ของแต่ละ chunk: `id`, `doc`, `clause`, `chapter`, `pages`, `text`
- [ ] `pipeline.py` + คำสั่ง `campusai ingest`
  - ต่อขั้นตอน: ดึงข้อความ → OCR เฉพาะหน้าที่ต้องทำ → clean → chunk
  - เขียนผลลง `data/processed/chunks.jsonl` และ `data/processed/<เอกสาร>.md` ไว้เปิดตรวจด้วยตา
  - มี flag `--force-ocr` (OCR ทุกหน้า) และ `--only <ไฟล์>`
  - รายงานสรุป: จำนวนหน้า, หน้าที่ OCR, จำนวน chunk, chunk ที่สั้นหรือยาวผิดปกติ
- [ ] Test ของ `clean` ทุกกฎ และ `chunker` อย่างน้อย 5 กรณี: ปกติ, ข้อ N/M, บรรทัดอ้างอิงลวง, ข้อยาว, ไม่มีโครงสร้าง

**เสร็จเมื่อ**
- `ingest` ได้ครบทุกเอกสาร และรันซ้ำแล้วได้ผลเหมือนเดิมทุกครั้ง
- เปิดไฟล์ `.md` สุ่มดูแล้ว chunk ตัดตรงหัวข้อจริง

### Phase 2: Retrieval

เป้าหมาย: ค้นเจอ chunk ที่ถูกต้องในอันดับต้น ๆ ทั้งคำถามแบบระบุเลขข้อและแบบภาษาธรรมชาติ พร้อมตัวเลขยืนยัน

#### #4 `feat/eval-dataset`

งานนี้ส่วนใหญ่เป็นการอ่านระเบียบแล้วเขียนคำถามเอง (ไม่ใช่เขียนโค้ด) ทำคู่กับ #5 ได้

**ทำอะไร**
- [ ] กำหนดรูปแบบ `eval/questions.jsonl` แต่ละบรรทัดมี:
  ```json
  {"id": "q001", "question": "...", "type": "direct",
   "expected": [{"doc": "ระเบียบวินัยนักศึกษา", "clause": "ข้อ 15"}],
   "reference_answer": "..."}
  ```
  ใช้ "เอกสาร + เลขข้อ" แทน chunk id เพื่อให้ชุดนี้ยังใช้ได้เมื่อเปลี่ยนวิธีแบ่ง chunk
- [ ] เขียนคำถาม 60–100 ข้อ แบ่ง 4 ประเภท:
  - `direct`: ถามเลขข้อตรง ๆ ("ข้อ 15 ว่าด้วยอะไร")
  - `semantic`: ถามภาษาธรรมชาติ ("ลอกข้อสอบเพื่อนโดนลงโทษยังไง")
  - `multi`: ต้องใช้หลายข้อประกอบกัน (เช่น กฎทั่วไป + ข้อยกเว้น)
  - `unanswerable`: เอกสารไม่มีคำตอบ (`expected` เป็น `[]`)
- [ ] สคริปต์ตรวจความถูกต้องของไฟล์: รูปแบบถูก และ `doc`/`clause` ที่อ้างมีอยู่ใน `chunks.jsonl` จริง

**เสร็จเมื่อ**: ครบทั้ง 4 ประเภท ประเภทละไม่น้อยกว่า 10 ข้อ และสคริปต์ตรวจผ่าน

#### #5 `feat/search-indexes`

**ทำอะไร**
- [ ] `embedder.py`: โหลด `bge-m3` ครั้งเดียว (lazy), encode เป็นชุด, normalize vector, ใช้ MPS ถ้ามี
- [ ] ข้อความที่ใช้ embed = ชื่อเอกสาร + หมวด + เลขข้อ + เนื้อหา (ให้ chunk ที่สั้นมีบริบทพอ)
- [ ] `vector_store.py`: Qdrant, cosine, 1024 มิติ, เก็บ metadata ไว้ใน payload, id แบบ deterministic (uuid5 จาก chunk id)
  - สลับได้ 2 โหมดผ่าน `QDRANT_MODE` ใน `.env`:
    - `local` (ค่าเริ่มต้น): `QdrantClient(path=QDRANT_PATH)` เก็บเป็นไฟล์ที่ `data/qdrant/`
    - `cloud`: `QdrantClient(url=QDRANT_URL, api_key=QDRANT_API_KEY)` ใช้ Qdrant Cloud (มี free tier 1GB)
  - โค้ดส่วนอื่น (`hybrid.py`, `cli.py`) เรียกผ่าน interface เดียวกัน ไม่ต้องรู้ว่าอยู่โหมดไหน
  - เพิ่มตัวแปรใน `.env.example`: `QDRANT_MODE`, `QDRANT_PATH`, `QDRANT_URL`, `QDRANT_API_KEY`
- [ ] `bm25.py`: ตัดคำด้วย PyThaiNLP `newmm`, ตัดช่องว่าง/เครื่องหมายวรรคตอนออก, BM25Okapi, สร้างจาก `chunks.jsonl` ตอนเริ่มโปรแกรม
- [ ] คำสั่ง `campusai index`: สร้าง index ใหม่จาก `chunks.jsonl`
- [ ] Test: tokenizer, BM25 จัดอันดับถูกบนชุดข้อมูลเล็ก, vector store (ใช้ Qdrant in-memory + vector ปลอม, ไม่ต้องต่อ Cloud จริงตอนรัน test)

**เสร็จเมื่อ**: `index` สร้างได้ทั้งสองโหมด (local และ cloud) และค้นแต่ละวิธีแยกกันแล้วได้ผลพร้อม metadata

#### #6 `feat/hybrid-search`

**ทำอะไร**
- [ ] `hybrid.py`: ดึง top-20 จากแต่ละวิธี แล้วรวมด้วย Reciprocal Rank Fusion (k=60)
- [ ] ถ้าคำถามระบุ `ข้อ N` / `มาตรา N` (รวมเลขไทย) ให้ดัน chunk ที่เลขข้อตรงกันขึ้นก่อน
- [ ] คำสั่ง `campusai search "..."`: แสดงอันดับจาก vector, BM25 และ hybrid เทียบกัน ไว้ debug
- [ ] `retrieval_eval.py` + คำสั่ง `campusai eval retrieval`
  - วัด Hit@1, Hit@3, Hit@5, MRR ของทั้ง 3 วิธี แยกตามประเภทคำถาม
  - เซฟผลเป็น `eval/results/retrieval-<วันที่>.md` และ `.json`
- [ ] Test: RRF กับอันดับที่รู้คำตอบ, การดึงเลขข้อจากคำถาม

**เสร็จเมื่อ**: ได้ตารางเปรียบเทียบ และ hybrid ได้ Hit@5 ไม่ต่ำกว่าวิธีที่ดีที่สุดในสองวิธี ถ้าต่ำกว่าต้องหาสาเหตุก่อน merge

### Phase 3: Generation

เป้าหมาย: ตอบคำถามจากเอกสารเท่านั้น อ้างอิงถูกต้อง และไม่เดา

#### #7 `feat/answer-generation`

**ทำอะไร**
- [ ] `answer.py`: prompt ภาษาไทย
  - system: ตอบจาก "เอกสารอ้างอิง" เท่านั้น, ใส่ `[n]` ท้ายประโยคที่เป็นข้อเท็จจริง, ถ้าไม่มีข้อมูลให้ตอบว่า "ไม่พบข้อมูลที่เกี่ยวข้องในเอกสารที่มี", ถ้ามีข้อมูลบางส่วนให้บอกชัดว่าส่วนไหนไม่มี
  - context: `[n] (เอกสาร, ข้อ, หน้า)` ตามด้วยเนื้อหา
- [ ] เรียก Gemini (ชื่อรุ่นอ่านจาก `.env`), temperature ต่ำ, retry แบบเว้นระยะนานขึ้นเรื่อย ๆ เมื่อเจอ 429/500/503
- [ ] ถ้าค้นไม่เจออะไรเลย ตอบว่าไม่พบข้อมูลโดยไม่เรียก LLM
- [ ] ดึงเลข `[n]` จากคำตอบ แล้วแสดงเฉพาะแหล่งที่ถูกอ้างจริง
- [ ] คำสั่ง `campusai ask "..."` และ `campusai chat` (โหลดโมเดลครั้งเดียว, มีคำสั่ง `/sources` ไว้ดูข้อความต้นฉบับ)
- [ ] Test: สร้าง prompt, ดึงเลขอ้างอิง, กรณีไม่มี context (mock Gemini)

**เสร็จเมื่อ**
- ถามคำถามจริง 10 ข้อแล้วได้คำตอบพร้อมอ้างอิงที่ถูกต้อง
- คำถามที่ไม่มีคำตอบในเอกสารต้องได้ข้อความปฏิเสธ

#### #8 `feat/answer-eval`

**ทำอะไร**
- [ ] `answer_eval.py` + คำสั่ง `campusai eval answers`
- [ ] ตัววัด:
  - **Faithfulness**: ทุกข้อความในคำตอบมีอยู่ใน context จริง (ไม่แต่งเพิ่ม)
  - **Correctness**: ตรงกับ `reference_answer` (ให้ LLM เป็นกรรมการ ให้คะแนน 1–5)
  - **Refusal accuracy**: คำถาม `unanswerable` ต้องถูกปฏิเสธ และคำถามที่มีคำตอบต้องไม่ถูกปฏิเสธ
  - **Citation accuracy**: `[n]` ที่อ้างชี้ไปที่ข้อที่ถูกต้อง
- [ ] ใช้ Gemini เป็นกรรมการ (หรือ RAGAS ถ้าใช้กับ Gemini ได้สะดวก)
- [ ] **cache คำตอบและคะแนนทุกข้อลงดิสก์ และคุมจังหวะการเรียก** จะได้ไม่ติด limit ซ้ำเหมือนเวอร์ชันเก่า
- [ ] เซฟผลเป็น `eval/results/answers-<วันที่>.md` พร้อมตัวอย่างข้อที่ตอบผิด

**เสร็จเมื่อ**: รันครบทั้งชุดได้ หยุดกลางทางแล้วรันต่อได้ และมีตารางผลรอบแรก (baseline)

## 3. ความเสี่ยงและแผนสำรอง

| ความเสี่ยง | สัญญาณ | แผนสำรอง |
|---|---|---|
| Typhoon OCR 3B อ่านบางหน้าผิดมาก | สุ่มตรวจแล้วเจอคำผิดเยอะ | ลองรุ่น 7B (`scb10x/typhoon-ocr-7b`) เฉพาะหน้าที่มีปัญหา หรือใช้ API ของ opentyphoon.ai ร่วมกับ cache |
| OCR ช้าเกินไป | เอกสารหลายร้อยหน้า | รันข้ามคืน (cache ทำให้หยุดแล้วรันต่อได้) และ OCR เฉพาะหน้าที่จำเป็น |
| เอกสารไม่มีโครงสร้างข้อ/มาตรา | chunker ตกไปใช้ fallback บ่อย | เพิ่มรูปแบบหัวข้อ (เช่น `1.`, `(1)`) ตามเอกสารจริง |
| Gemini ติด limit ตอน eval | ได้ 429 ต่อเนื่อง | cache + คุมจังหวะ, รันเป็นช่วง หรือใช้ Flash-Lite เป็นกรรมการ |
| ชื่อรุ่น Gemini เปลี่ยน/เลิกให้บริการ | เรียกแล้ว error ว่าไม่มีรุ่นนี้ | เปลี่ยน `GEMINI_MODEL` ใน `.env` ไม่ต้องแก้โค้ด |
| แรม 16GB ไม่พอ | เครื่องช้าหรือ swap หนัก | ไม่รัน Ollama พร้อมกับ bge-m3 (OCR เสร็จก่อนค่อย index) |
